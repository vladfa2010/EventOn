# ЛЛМ-блок: поиск свежих событий через Kimi

Живёт целиком в `server.js` (функции `chat`, `askKimi`) + клиентский опрос в `fillAround`. Задача: по координатам пользователя найти реальные арт-события города, которые можно посетить сегодня/завтра.

## Почему такая архитектура: фоновые задачи + опрос

Поиск с веб-поиском занимает 20 секунд – 5 минут. Длинный HTTP-запрос на это время рвут прокси и браузеры — на клиенте это выглядело как `Failed to fetch`. Поэтому:

```
клиент GET /api/around ──► сервер: мгновенный ответ {ok, pending:true, city}
                           сервер: запуск фоновой задачи (jobs Map)
клиент: повторный GET каждые 10 с (до 60 раз)
   ◄── {pending:true}            — задача ещё ищет
   ◄── {ok, city, events[], cached} — готово
   ◄── {ok:false, error}         — ошибка (5 минут отдаётся как есть)
```

Каждый отклик мгновенный — рвать нечего. Ключ задачи и кэша: `город:дата` (поиск привязан к дню).

## Запрос к Kimi API

- **Endpoint**: `https://api.moonshot.ai/v1/chat/completions` (OpenAI-совместимый).
- **Модели**: `MODELS=['kimi-k2.6','moonshot-v1-32k']` — перебор по кругу, пока одна не ответит. k3 не используем (баг echo: `tokenization failed`), `k2-0711-preview` недоступен на ключе.
- **Параметры запроса**: только `max_tokens:8192` + `thinking:{type:'disabled'}`. **temperature/top_p/penalties не шлём никогда** — у k2.6 они зафиксированы платформой (thinking: temp=1.0; non-thinking: temp=0.6, top_p=0.95), чужое значение = ошибка API.
- **`thinking:'disabled'` — ключевой фикс стабильности**: non-thinking режим фиксирует temp=0.6 вместо 1.0, вариативность падает в разы. До фикса: серии из 5+ пустых ответов подряд, 150–316 с на поиск. После: 3/3 города с первой попытки за 22–43 с. (`reasoning_effort:'low'` до этого просто игнорировался API.)

## Цикл веб-поиска (`$web_search`)

Встроенный инструмент платформы; своя логика поиска не нужна:

```js
tools=[{type:'builtin_function',function:{name:'$web_search'}}] // в КАЖДОМ раунде
// цикл, пока finish_reason==='tool_calls':
// 1. assistant-сообщение добавляем в контекст целиком (с reasoning_content)
// 2. отвечаем {role:'tool', tool_call_id, name, content:JSON.stringify(arguments)}
//    — аргументы эхом, дословно; поиск выполняет платформа
// finish_reason==='stop' → парсим итоговый JSON
```

## Промпт (system)

Городская арт-афиша. Ключевые требования:
- искать события, доступные **сегодня или завтра**, включая идущие сейчас выставки;
- **минимум 2–3 поисковых запроса разными словами** — на языке страны города и по-английски («афиша», «выставки», «что посмотреть» + город);
- не сдаваться после первого пустого поиска;
- ответ — строго JSON-массив до 8 элементов `{title, venue, date, url, kind}`, без markdown и рассуждений.

## Парсинг ответа (`parseArr`)

Модель при temp≠0 иногда оборачивает JSON в мусор (рассуждения, `<details>`-блоки). Поэтому: пробуем распарсить весь текст → если не вышло, вытаскиваем все `[...]`-кандидаты регэкспом и пробуем от самого длинного. Пустой/битый результат ≠ ошибка — повод для следующей попытки.

## Ретраи на двух уровнях

**Внутри `askKimi(city, budgetMs)`** (бюджет по умолчанию 5 мин):
1. До 4 раундов диалога;
2. Если пусто — 2 «подталкивания» (`NUDGES`: пользовательские сообщения с другими русскими поисковыми подсказками), каждое ещё до 2 раундов;
3. Всё ограничено жёстким дедлайном `budget`.

**На уровне задачи** (`/api/around`, общий дедлайн 8 мин):
```
while (нет событий && осталось > 60 с):
    [r1, r2] = Promise.allSettled([askKimi(city, left), askKimi(city, left)])  // 2 параллельно
    объединить, дедуп по url, slice(0, 8)
```
Дублирование гасит остаточную вариативность: пустой итог обеих веток маловероятен.

## Кэш

- **Ключ**: `город.toLowerCase() + ':' + new Date().toDateString()`.
- **TTL**: найденное — 12 ч (`CACHE_TTL`); пустой результат — 5 мин (одна неудача не глушит город на полдня).
- Ответ с флагом `cached:true` — клиент показывает «· кэш».

## Геокодинг (без ключей API)

| Шаг | Сервис | Детали |
|---|---|---|
| Primary | Nominatim (OSM) | `accept-language=ru`, троттлинг 1 req/s, таймаут 6 с, circuit-breaker 10 мин после сбоя |
| Fallback | Photon (komoot) | 3 попытки, бэкофф 2,5 с (переживает 503) |

- `reverseCity(lat,lng)` — приоритет типов `city > town > village > municipality > district > county > state` по всем фичам; срезается префикс «городской округ ». Кэш по координатам, округлённым до 0,1°.
- `forwardCity(q)` — ручной ввод города → координаты.
- В `/api/around` результат `reverseCity` **авторитетно перекрывает** клиентский параметр `city` — «вместо Екатеринбурга Москва» больше невозможна.

## Подписка (`/api/subscribe`)

`POST {email, city}` → строка `ISO;email;city` в `subscribers.csv`. Рассылка не отправляется — только сбор. Файл закрыт от раздачи (404) и в `.gitignore`.

## Что видит пользователь (клиентская часть)

1. Заглушка «ИИ Мы ищем культурные события вокруг вас» (половинная ширина) + карточка почты второй.
2. Опрос каждые 10 с; успех → полная перерисовка карусели свежими событиями с бейджем «ИИ».
3. Ошибка → честный «Kimi недоступен: {причина}» + база ≤500 км остаётся.
4. Логи сервера (`[/api/around] город — найдено: N (заходов: X, Yс)`) видны в логах Render.
